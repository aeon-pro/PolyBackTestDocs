## Time Filtering

Most endpoints return time-series data - market snapshots, orderbooks, trades. Use `start_time` and `end_time` to focus a query on a specific window.

The API accepts timestamps in two formats:
1. **Millisecond Epoch**: e.g., `1709006400000` (recommended for programmatic access)
2. **ISO8601 String**: e.g., `2026-02-27T04:00:00Z` (useful for manual testing)

### Query Parameters

| Parameter | Type | Description |
| :--- | :--- | :--- |
| `start_time` | string \| integer | Return records **after** this timestamp. |
| `end_time` | string \| integer | Return records **before** this timestamp. (Defaults to now on Binance endpoints if omitted.) |

**Example:** Fetching snapshots for a specific BTC market in January 2026

```bash
curl "https://api.polybacktest.com/v3/btc/markets/1051520/snapshots?start_time=2026-01-01T00:00:00Z&end_time=2026-01-31T23:59:59Z" \
  -H "X-API-Key: $POLY_KEY"
```

**Example:** Fetching the last hour of ETH spot trades using epoch timestamps

```bash
curl "https://api.polybacktest.com/v3/eth/spot/trades?start_time=1708992000000&end_time=1708995600000" \
  -H "X-API-Key: $POLY_KEY"
```

<Tip>
The coin is now a path segment (`/v3/{coin}/...`), not a query parameter. Every v3 request picks a single coin at the URL level.
</Tip>

## Pagination

v3 uses **cursor pagination** (keyset / seek) instead of v2's `limit`/`offset`. Cursors stay O(1) at any depth, hit the same DB indexes, and remain stable under concurrent writes.

| Parameter | Default | Maximum | Description |
| :--- | :--- | :--- | :--- |
| `limit` | Varies | Varies | Number of results per page. |
| `cursor` | - | - | Opaque cursor from the previous response's `pagination.next_cursor`. |
| `include_count` | `false` | - | Set `true` to populate `pagination.total_count` (triggers a `COUNT(*)` - avoid unless needed). |

### Maximum Limits

Different endpoints cap the `limit` to protect backend performance:
- **List Markets**: Max `100` markets per request.
- **Snapshots & Binance Data**: Max `1000` records per request.

### Response shape

Every paginated response looks like this:

```json
{
  "data": [ { "market_id": "1051520", "...": "..." } ],
  "pagination": {
    "next_cursor": "eyJzdCI6IjIwMjYtMDEtMDFUMDA6MDA6MDBaIiwiaWQiOiIxMDUxNTIwIn0",
    "has_more": true,
    "limit": 1000,
    "count": 1000
  },
  "meta": { "request_id": "req_a1b2c3d4e5f6", "timestamp": "2026-04-16T12:00:00Z" }
}
```

Stop paginating when `pagination.has_more === false`.

### How to Paginate

Take the `pagination.next_cursor` from one response and pass it back as `?cursor=` on the next request. No offset arithmetic, no risk of skipped or duplicated rows.

**Example Python Pagination Loop:**

```python
import requests

market_id = "1051520"
base_url = f"https://api.polybacktest.com/v3/btc/markets/{market_id}/snapshots"
headers = {"X-API-Key": "YOUR_API_KEY"}

limit = 1000
cursor = None
all_snapshots = []

while True:
    params = {"limit": limit, "start_time": "2026-01-01T00:00:00Z"}
    if cursor:
        params["cursor"] = cursor

    body = requests.get(base_url, headers=headers, params=params).json()
    all_snapshots.extend(body["data"])

    if not body["pagination"]["has_more"]:
        break
    cursor = body["pagination"]["next_cursor"]

print(f"Total snapshots fetched: {len(all_snapshots)}")
```

<Warning>
The legacy v2 `?offset=N` parameter still works on v3 endpoints for back-compat, but is deprecated. Mixing `offset` and `cursor` is not supported - if both are provided, `cursor` wins.
</Warning>

## Best Practices

### 1. Polling for Live Data vs. Backfilling

- **Backfilling History:** When pulling days or weeks of historical data, always provide explicit `start_time` / `end_time` bounds, use the maximum `limit`, and step through with the cursor.
- **Polling for Live Data:** When continuously polling for the latest updates, omit `end_time` and use `limit=1`, or dynamically move `start_time` forward based on the timestamp of the last record you received.

### 2. Including Orderbooks Wisely

For the Polymarket snapshot endpoint, orderbooks are excluded by default (`include_orderbook=false`) to keep responses small and fast.

- If you only need price histories (OHLC-style analysis), keep it `false`.
- If you're backtesting liquidity or order-flow strategies, set `include_orderbook=true`, but expect significantly larger payloads. Drop `limit` to avoid timeouts.

### 3. Don't opt into `total_count` unless you need it

`COUNT(*)` on large tables is expensive. v3 omits `total_count` by default. Only pass `?include_count=true` when you actually display a "page X of Y" - for infinite-scroll, cursor-based UIs, don't bother.

### 4. Millisecond Epoch over ISO

ISO8601 strings are human-readable and good for manual testing. For production systems, use millisecond epoch integers - no time-zone ambiguity and a faster parse on both ends.

### 5. Batch where it helps

If your page load fans out several independent GETs (e.g. latest BTC spot + latest ETH futures + BTC markets list), consider `POST /v3/batch` to collapse them into one round trip. Each sub-request still counts as one rate-limit hit. See the [Batch endpoint docs](/api-reference/v3/batch).
