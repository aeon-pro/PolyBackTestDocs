## Fan out up to 10 GETs in a single round trip

```json
{
  "requests": [
    { "id": "r1", "path": "/v3/btc/markets?type=5m&limit=10" },
    { "id": "r2", "path": "/v3/eth/markets?type=15m&limit=5" },
    { "id": "r3", "path": "/v3/sol/markets?type=5m&limit=5" }
  ]
}
```

Response:

```json
{
  "data": [
    { "id": "r1", "status": 200, "body": { "data": [...], "pagination": {...}, "meta": {...} } },
    { "id": "r2", "status": 200, "body": { "data": {...}, "meta": {...} } },
    { "id": "r3", "status": 403, "body": { "error": { "code": "COIN_NOT_IN_PLAN", "message": "..." }, "meta": {...} } }
  ],
  "meta": { "request_id": "req_...", "timestamp": "..." }
}
```

## Rules

- **Max 10** sub-requests per batch. More than that returns `BATCH_TOO_LARGE`.
- **GET only**. Other methods are not allowed.
- Paths must be **relative v3 paths** starting with `/v3/`. No nested `/v3/batch`.
- **Each sub-request counts as one rate limit hit.** A batch of 10 reserves 10 slots up front.
- Outer HTTP status is **always 200** - inspect each `data[].status` for per-sub-request outcomes.

<Warning>Sub-request ids must be unique within a batch. Duplicates return `BATCH_INVALID_PATH`.</Warning>
